# Rod Validation

[Crates.io](https://crates.io/crates/rod_validation)
[Documentation](https://docs.rs/rod_validation)
[![License: GPL v3](https://img.shields.io/badge/License-GPLv3-blue.svg)](https://github.com/kommade/rod/blob/master/LICENSE)

A powerful and flexible compile-time validation library for Rust structs and enums. Rod provides declarative validation through derive macros, allowing you to specify validation rules directly in your type definitions.

## Features

- **Compile-time validation**: Validation rules are checked at compile time for type safety
- **Declarative syntax**: Define validation rules using intuitive attribute macros
- **Comprehensive type support**: Validate strings, integers, floats, options, tuples, and custom types
- **Flexible error handling**: Choose between fail-fast or collect-all error reporting
- **Custom validation**: Add custom validation logic with closures
- **Regex support**: Built-in regex validation for strings (with optional `regex` feature)
- **Nested validation**: Support for complex nested data structures
- **Per-validation custom errors**: Attach tailored messages to individual validation rules for precise feedback
- **Validation groups**: Tag fields with `group = "..."` and validate them selectively (multi-step forms, wizards)
- **Combinators**: `any`/`one`-of, conditional, cross-field and pipeline validation helpers
- **Field metadata**: Compile-time `RodMetadata` describing every validated field, for form/UI generation
- **Validation metrics**: Measure validation duration and count failures
- **JSON Schema export**: The derive generates `ToJsonSchema` implementations (with the `serde` feature)
- **Async-ready**: An `AsyncValidator` trait generated by the derive, with optional `async_check` field closures for truly async rules

## Quick Start

Add Rod Validation to your `Cargo.toml`:

```sh
cargo add rod_validation
```

For regex support:

```sh
cargo add rod_validation --features regex
```

For JSON Schema export:

```sh
cargo add rod_validation --features serde
```

## Basic Usage

```rust
use rod_validation::prelude::*;

#[derive(RodValidate)]
struct User {
    #[rod(String {
        length: 3..=50,
        format: Email,
    })]
    email: String,
    
    #[rod(String {
        length: 8..=100,
        includes: "@",
    })]
    password: String,
    
    #[rod(i32 {
        size: 18..=120,
        sign: Positive,
    })]
    age: i32,
    
    #[rod(Option {
        String {
            length: 1..=100,
        }
    })]
    bio: Option<String>,
}

fn main() {
    let user = User {
        email: "user@example.com".to_string(),
        password: "secure@password123".to_string(),
        age: 25,
        bio: Some("Software developer".to_string()),
    };
    
    // Validate and get first error (fail-fast)
    match user.validate() {
        Ok(_) => println!("User is valid!"),
        Err(e) => println!("Validation error: {}", e),
    }
    
    // Validate and collect all errors
    match user.validate_all() {
        Ok(_) => println!("User is valid!"),
        Err(errors) => {
            println!("Found {} validation errors:", errors.len());
            for error in errors {
                println!("  - {}", error);
            }
        }
    }
}
```

## Validation Types

### String Validation

```rust
#[derive(RodValidate)]
struct StringExample {
    #[rod(String {
        length: 5..=20,           // Length between 5 and 20 characters
        format: Email,            // Built-in email format (requires regex feature)
        starts_with: "user_",     // Must start with "user_"
        ends_with: "@domain.com", // Must end with "@domain.com"
        includes: "test",         // Must contain "test"
    })]
    field: String,
}
```

Available string formats (with `regex` feature):

- `Email` - Email address validation
- `Url` - URL validation  
- `Uuid` - UUID validation
- `Ipv4` - IPv4 address validation
- `Ipv6` - IPv6 address validation
- `DateTime` - DateTime validation
- A string literal, e.g. `format: r"^[A-Z]{3}$"` - Custom regex pattern

### Integer Validation

```rust
#[derive(RodValidate)]
struct IntegerExample {
    #[rod(i32 {
        size: 1..=100,    // Value between 1 and 100
        sign: Positive,   // Must be positive
        step: 5,          // Must be multiple of 5
    })]
    field: i32,
}
```

Number signs:

- `Positive` - Greater than 0
- `Negative` - Less than 0  
- `NonPositive` - Less than or equal to 0
- `NonNegative` - Greater than or equal to 0

### Float Validation

```rust
#[derive(RodValidate)]
struct FloatExample {
    #[rod(f64 {
        size: 0.0..=100.0,  // Value between 0.0 and 100.0
        sign: NonNegative,  // Must be non-negative
        ftype: Finite,       // Must be finite (not NaN or infinite)
    })]
    field: f64,
}
```

Float types:

- `Finite` - Not NaN or infinite
- `Infinite` - Must be infinite
- `Nan` - Must be NaN
- `Normal` - Must be normal
- `Subnormal` - Must be subnormal

### Option Validation

```rust
#[derive(RodValidate)]
struct OptionExample {
    // Validate the inner value if Some
    #[rod(Option {
        String {
            length: 5,
        }
    })]
    optional_field: Option<String>,
    
    // Require the field to be None
    #[rod(Option {})]
    must_be_none: Option<String>,
}
```

### Tuple Validation

```rust
#[derive(RodValidate)]
struct TupleExample {

            length: 5,
        },

            size: 0.0..=1.0,
        }
    ))]

}
```

### Literal Validation

```rust
#[derive(RodValidate)]
struct LiteralExample {

```

### Custom Validation

```rust
#[derive(RodValidate)]

            size: 1..=100,

```

### Iterable Validation

```rust

```

## Error Handling

Rod provides two validation methods:

- `validate()` - Returns the first validation error encountered (fail-fast)
- `validate_all()` - Collects and returns all validation errors

```rust
// Fail-fast validation
match user.validate() {
    Ok(_) => println!("Valid!"),
    Err(error) => println!("Error: {}", error),
}

// Collect all errors
match user.validate_all() {
    Ok(_) => println!("Valid!"),
    Err(errors) => {
        for error in errors.iter() {
            println!("Error: {}", error);
        }
    }
}
```

## Per-Validation Custom Errors

Attach bespoke error messages to any validation rule using the `? "<error>"` syntax. Messages placed immediately before a rule override its default error output.

```rust
#[derive(RodValidate)]
struct SignupForm {
    #[rod(String {
        ? "Password must be at least eight characters long.",
        length: 8..,
        ? "Password must include the @ symbol for legacy compatibility.",
        includes: "@",
    })]
    password: String,
}
```

The custom messages are surfaced by both `validate` and `validate_all`, making it straightforward to deliver user-friendly, context-aware feedback.

You may also override the error messages for all validation rules of a type with the `message: "<error>"` syntax.

```rust
#[derive(RodValidate)]
struct SignupForm {
    #[rod(
        String {
            length: 8..,
            includes: "@",
        },
        message: "Password must be 8 characters AND have an @"
    )]
    password: String,
}
```

If both error message syntaxes are attached, messages attached to specific rules will be preferred.

## Nested Structures

Rod supports validation of nested structures that implement `RodValidate`:

```rust
#[derive(RodValidate)]
struct Address {
    #[rod(String { length: 1..=100 })]
    street: String,
    
    #[rod(String { length: 2..=50 })]
    city: String,
}

#[derive(RodValidate)]
struct Person {
    #[rod(String { length: 1..=50 })]
    name: String,
    
    // No #[rod] attribute needed for custom types
    address: Address,
}
```

## Enums

Rod supports validation of enumeration variants:

```rust
#[derive(RodValidate)]
enum Status {
    #[rod(String { length: 1..=100 })]
    Active(String),
    
    Inactive,
    
    #[rod(i32 { size: 1..=30 })]
    Pending { days: i32 },
}
```

## Validation Groups

Tag fields with `group = "name"` and validate them selectively — handy for multi-step forms and wizards. Fields **without** a group always participate, no matter which group is requested.

```rust
use rod_validation::prelude::*;

#[derive(RodValidate)]
struct Signup {
    #[rod(
        group = "account",
        String {
            length: 5..=10,
        }
    )]
    username: String,
    #[rod(
        group = "account",
        String {
            length: 8,
        }
    )]
    password: String,
    #[rod(i32 {
        size: 18..=99,
    })]
    age: i32,
}

// Validates `username` + `password` (group "account") and `age` (ungrouped)
signup.validate_group("account")?;

// Validates every field, ignoring groups
signup.validate_all_groups()?;
```

Group-aware validation is generated by the derive only for types that use `group` tags; other types fall back to validating everything.

## Validation Combinators

The derive attributes describe *per-field* rules, but some checks need composition: run a validator only in a certain state, compare several fields with each other, accept one of several alternatives, or combine independent validations into one report. The `RodValidateExt` trait adds these as **plain methods on the value** — it is blanket-implemented on every `RodValidate` type, and everything is re-exported through the prelude:

```rust
use rod_validation::prelude::*;

#[derive(RodValidate, Clone)]
struct Draft {
    #[rod(String { length: 3..=20 })]
    title: String,
}

let draft = Draft { title: "a draft".to_string() };

// Only validate in a particular state (e.g. at submit time):
draft.clone().validate_if(is_submitting)?;   // skipped -> Ok(())
draft.clone().validate_unless(is_archived)?; // inverse condition

// At least one / exactly one of several checks must pass:
draft.clone().validate_any(&[|d: &Draft| d.validate()])?;
draft.clone().validate_one(&[|d: &Draft| d.validate()])?;

// Ad-hoc and cross-field checks (sees the whole value):
draft.validate_with(|d| {
    if d.title.contains("draft") { Ok(()) }
    else { Err(RodValidateError::CheckFailed("title must mention draft")) }
})?;
```

### Any / one-of

`validate_any` succeeds as soon as one check passes and otherwise reports the last error; `validate_one` requires **exactly one** success (XOR semantics — several matches usually indicate corrupt data). Checks are passed as a homogeneous slice, so when mixing closures and named functions, annotate it:

```rust
let checks: [fn(&Draft) -> Result<(), RodValidateError>; 2] = [first_check, second_check];
draft.validate_one(&checks)?;
```

### Running checks conditionally

`validate_if(cond)` runs the normal validation only while `cond` holds and returns `Ok(())` otherwise — e.g. a draft form is only checked once the user submits. `validate_unless(cond)` is the inverse. Both consume the value, just like `validate`.

### Cross-field and ad-hoc checks

`validate_with` runs a closure against the whole value, which is how you express rules spanning several fields (invariants like `low <= high`, two dates ordered, confirmation matches). It accepts any error type convertible into `RodValidateError`:

```rust
use rod_validation::prelude::*;

#[derive(RodValidate)]
struct Range {
    #[rod(i32 { size: 0.. })]
    low: i32,
    #[rod(i32 { size: 0.. })]
    high: i32,
}

let range = Range { low: 1, high: 10 };
range.validate_with(|r| {
    if r.low <= r.high {
        Ok(())
    } else {
        Err(RodValidateError::UserDefined("`low` must not exceed `high`".into()))
    }
})?;
```

### Validation pipeline

When a single `validate_all` call is not enough — e.g. field rules **plus** a group **plus** an ad-hoc invariant, all funnelled into one report — build a `ValidationPipeline`. Errors accumulate into the same `RodValidateErrorList` that `validate_all` returns, so the result composes with everything else:

```rust
let errors = user.pipeline()
    .step(|u| u.validate())                     // a fail-fast validation
    .step_all(|u| u.validate_group("billing"))  // ...plus a whole group's errors
    .step(|u| if u.expired() {
        Err(RodValidateError::UserDefined("account expired".into()))
    } else {
        Ok(())
    })                                          // ...plus ad-hoc rules
    .result()?;                                 // Result<(), RodValidateErrorList>
```

Use `.all_errors()` instead of `.result()` when you want the collected list without the `Result` wrapper.

## Field Metadata & Metrics

The derive generates `impl RodMetadata` exposing static metadata about every validated field — no runtime reflection:

```rust
use rod_validation::prelude::*;

// Compile-time metadata: name, group, required
for field in Signup::FIELDS {
    println!(
        "{} (group: {:?}, required: {})",
        field.name, field.group, field.required
    );
}

// Helpers via the blanket-implemented ValidationMetadata trait
signup.required_fields();   // ["username", "password", "age"]
signup.optional_fields();   // fields declared as `Option { ... }`  
<Signup as ValidationMetadata>::fields_in_group("account");
```

`Option { ... }` fields are reported as not required; `#[rod(skip)]` fields are excluded entirely. Metrics measure real validation runs:

```rust
let run = signup.validate_with_metrics();
println!(
    "checked {} fields, {} failures, took {} ms",
    run.checks, run.failures, run.duration_ms
);
```

## JSON Schema Export

With the `serde` feature, the derive also generates a `ToJsonSchema` implementation describing every field's rules as draft 2020-12 JSON Schema — ready for OpenAPI docs, editor tooling, or frontend form generation:

```toml
[dependencies]
rod_validation = { version = "0.4.0", features = ["serde"] }
```

```rust
// `serde_json::Value` implements `Display`; `{:#}` pretty-prints
println!("{:#}", Signup::to_json_schema());
```

renders:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "username": { "type": "string", "minLength": 5, "maxLength": 10 },
    "password": { "type": "string", "minLength": 8, "maxLength": 8 },
    "age": { "type": "integer", "minimum": 18, "maximum": 99 }
  },
  "required": ["username", "password", "age"]
}
```

Mapping summary:

- Strings/iterables: `minLength`/`maxLength`, `minItems`/`maxItems`, `items`
- Numbers: `minimum`/`maximum` (plus `exclusiveMaximum`/`exclusiveMinimum` for open ranges and signs), `multipleOf` for `step`
- `Literal { value }` → `const`; `Option {}` → `"type": "null"`; tuples → `prefixItems`; enums → `oneOf`
- Built-in formats → `format` (`email`, `uri`, `uuid`, `ipv4`, `ipv6`, `date-time`; requires `regex`), custom regex → `pattern`
- Custom `check` closures are not representable in JSON Schema and are omitted

## Async Validation

Every `#[derive(RodValidate)]` type implements `AsyncValidator`, providing a uniform async API for pipelines. It validates *everything*: all synchronous rules first, then every `async_check`, returning one combined error list:

```rust
let result = signup.validate_async().await;
```

Fields can additionally declare **async custom checks** with `async_check = |x| <future>` — the closure receives the field value and must return a `Send` future resolving to `bool` (e.g. a database lookup or an HTTP HEAD request):

```rust
#[derive(RodValidate)]
struct Signup {
    #[rod(
        group = "account",
        String {
            length: 5..=10,
        },
        // Sync rules never wait; async checks run only in `validate_async`.
        async_check = |u: &String| username_is_free(u)
    )]
    username: String,
    #[rod(
        String {
            length: 8,
        }
    )]
    password: String,
}
```

Types without `async_check` fields behave like `validate_all` inside the future. Because checks run against `&self`, the validated type must be `Sync`, and the returned future is always `Send` — safe to use with `tokio::spawn` and friends. The lowest-level hook, `run_async_checks`, can also be overridden manually to add whole-value async rules without touching the derive.

## The RodValidate Derive Macro

The `#[derive(RodValidate)]` macro generates the following for your types:

- `validate(&self) -> Result<(), RodValidateError>` - Fail-fast validation (returns on first error)
- `validate_all(&self) -> Result<(), RodValidateErrorList>` - Collect all errors before returning
- `validate_group(&self, group: &str) -> Result<(), RodValidateErrorList>` - Validate only fields tagged with the given group (plus ungrouped fields); generated when the type uses `group` tags, otherwise falls back to `validate_all`
- `validate_all_groups(&self) -> Result<(), RodValidateErrorList>` - Validate every field, regardless of groups
- `impl RodMetadata` - Static `FIELDS: &'static [RodFieldMeta]` metadata (name, group, required) for form/UI generation
- `impl ToJsonSchema` - JSON Schema export (generated only with the `serde` feature)
- `impl AsyncValidator` - Async counterpart: `validate_async()` runs all sync rules plus every `async_check` field closure

### Error Messages

The generated validation code produces detailed error messages with field paths:

```rust
// Example error: "Expected `user.email` to be a string with length 3..=50, got 2"
```

### Compilation Guarantees

The macro provides several compile-time guarantees:

1. **Type Safety**: Validation attributes must match the field type
2. **Nested Types**: Custom types must implement `RodValidate`
3. **Attribute Validation**: Invalid attribute combinations are caught at compile time

### Technical Details

#### Code Generation Strategy

The macro generates validation code that:

1. Traverses struct or enumeration fields recursively
2. Applies validation rules in the order they appear in attributes
3. Handles early return (fail-fast) or error collection (validate-all) modes
4. Provides detailed error context with complete field paths

#### Performance Considerations

- All validation logic is generated at compile time
- No runtime reflection or dynamic dispatch overhead
- Validation performance is equivalent to hand-written code
- Zero-cost abstractions for unused validation paths

#### Limitations

1. **Union types**: Not supported (will generate `todo!()` panic)
2. **Custom validation closures**: Must return `bool` type. Async closures (`async_check`) must return a `Send` future resolving to `bool`, and the type must be `Sync`

## Rust Features

- **Default features**: none
- **`regex`**: Enables regex-based string format validation
- **`serde`**: Enables generated JSON Schema export (pulls in `serde_json`)
